# Mobile performance audit, 26 November 2026 (T36)

Audit of the customer-facing pages after the redesign (Phase 14, D1 to D5), against the target in
`markdown/CONSTRAINTS.md` (Planned, T36): **LCP <= 2.5 s and CLS <= 0.1 on the key customer pages.**
The SPEC's Success Criteria hold no LCP or CLS number (only the streaming latency, <= 3 s, which is T33);
`markdown/design.md` ("Performance") repeats the 2.5 s target. Stack: Next.js 16.4.2 (Turbopack, Cache
Components, partial prefetching), next-intl, Supabase, Tailwind 4.

Nothing in the source was changed by this audit. The fixes below are proposals.

## Method

1. Read `markdown/CONSTRAINTS.md`, `CLAUDE.md`, `AGENTS.md`, `markdown/design.md`; read the Next.js 16 guide
   for `next/image` (`node_modules/next/dist/docs/01-app/03-api-reference/02-components/image.md`: `preload`,
   `fetchPriority`, `formats`).
2. Read the source of the key pages and their loaders (landing, services, pesan, pay, home, orders, live,
   recording, support, shells, fonts, `next.config.ts`).
3. `npm run build` (PowerShell): compile 14 s, TypeScript 30 s, 131 pages generated in 7.5 s, 65 s in all. The
   build then exits with code 1 (finding B). Compile, type check and page generation had finished, and
   `next start` runs on the output. Turbopack's route table has no size column, so route weights come
   from `.next` (client reference manifests, the prerendered HTML and the font manifest, gzip level 9
   at the optimal level, computed by script; the production host will likely send Brotli, which is smaller).
4. `npm run start -- --port 3100`, then Chromium driven through Playwright (already installed, no new
   dependency) with throttling through the DevTools protocol. LCP, CLS, FCP and long tasks come from
   PerformanceObserver; bytes from `Network.loadingFinished`. "What-if" runs abort chosen requests or
   rewrite one response in flight, to estimate a fix without changing source.
5. Image formats compared offline with the `sharp` that ships with Next (output in a temp folder).

Limits to keep in mind:

- Local server: no TLS, no CDN, HTTP/1.1 (the host will use HTTP/2 or 3), no real distance. The dynamic parts
  (`/services` catalog) were timed with the server and Supabase as they are on this machine.
- Chromium's own throttling, not Lighthouse's simulated throttling; numbers are comparable to each other, not
  to a PageSpeed score. A single dev machine; TBT in particular is noisy.
- The working tree had changes from another session when the build ran (e2e specs, `feed-tile.tsx`,
  `order-search-actions.ts`, message files, two test files); I did not make them, and the numbers reflect
  that tree.
- About a dozen anonymous page views of `/services`, `/home`, `/support` ran against the local build, which
  triggers the pages' normal read-only public queries (catalog, free windows, ratings). No sign-in, no
  writes, no database tool, no env file read by me.

## Findings

### 1. [HIGH] Retired fonts are preloaded on every page, ahead of the LCP image

- **Area:** Loading, Core Web Vitals (LCP).
- **Location:** `src/app/fonts.ts` (Bricolage Grotesque with `latin` and `latin-ext` plus the `opsz` axis,
  and Figtree with `latin` and `latin-ext`), imported by `src/app/[locale]/layout.tsx` lines 9 and 41;
  the font tokens in `src/app/globals.css` lines 93 to 94. Fonts actually used since D5: Inter, Inter Tight and
  Instrument Serif from `src/app/fonts-forest.ts`, which every route group now applies through
  `.theme-forest` (marketing, customer, auth, admin, agency, cleaner, owner layouts).
- **Description:** the only thing still using Bricolage and Figtree is `src/app/[locale]/not-found.tsx`, which
  sits outside the route groups. Next.js still preloads all four files on every route: the landing page
  response has a `Link: rel=preload; as=font` header for 7 files (`.next/server/app/id.meta`, and
  `next-font-manifest.json` lists the same 7 for every page). They are fetched at **High** priority in
  every run, while the LCP image is **Low**.
- **Impact (measured, lab):** 4 files, 138 KB on disk (Bricolage 76.9 + 30.6 KB, Figtree 20.2 + 10.2 KB),
  140 KB transferred, 24% of the landing page's 572 KB and 56% of its font bytes. Blocking those requests in
  a what-if run moved landing LCP from 2404 to 1896 ms (Pixel viewport) and from 1972 to 1676 ms (360 x 640),
  and removed 140 KB from every page's first load (also `/services`, `/login`).
- **Recommendation:** pick one.
  - Minimal: in `src/app/fonts.ts` set `preload: false` on both fonts. They stay available for the 404 page,
    but nothing is preloaded, so the Link headers drop to the 3 forest fonts.
  - Cleaner: delete `src/app/fonts.ts`, drop `appFontVariables` from the root layout, and give
    `not-found.tsx` the `theme-forest` wrapper and `forestFontVariables` like the route groups; point the
    default font tokens in `globals.css` (lines 93 to 94) at system fonts, and update
    `markdown/design.md` ("Performance", line 686) and `docs/frontend-map.md`.
  - Either way, check the 404 page by eye, and re-check the response header: it should list 3 fonts.

### 2. [HIGH] The Supabase browser client and Realtime ship on every customer page

- **Area:** Loading, JavaScript weight.
- **Location:** `src/components/support/use-realtime.ts` (static import of `@/lib/supabase/browser`, which
  pulls in `@supabase/ssr` and the Realtime client), used by `src/components/support/ticket-chat.tsx` and
  `src/components/admin/inbox-live.tsx`; the link that triggers it is `/support` in
  `src/components/shell/app-navigation.ts` line 24 (customer navigation).
- **Description:** chunk `3ulrj2gfnd97f.js` (275 KB raw, 73.9 KB gzip, contains `RealtimeClient`,
  `GoTrueClient`, `createBrowserClient`) belongs to the help page's chat. `/support` is linked from the
  customer navigation, so every page that shows it prefetches the route, and the prefetch loads that chunk.
  Measured: it is downloaded on `/login` and on the guest `/home`, which do not use it, and it is in
  `/support`'s own script list for every visitor, not only for those with a ticket. Authenticated pages
  were not measured but share the same navigation, so expect the same.
- **Impact (measured):** 74 KB gzip (about 30% of a page's JavaScript, 0.37 s of link time at 1.6 Mbps)
  plus parsing 275 KB of script on a slow CPU, competing with the page's own late work (for example the
  live video on `/orders/live`, which uses `preload="auto"`). `/support` goes from 166 KB to 240 KB gzip, past
  the 200 KB budget. It is a prefetch, so LCP is not hit, but TBT and the first interaction are.
- **Recommendation:** load the client only when a chat opens. In `use-realtime.ts`, replace the static import
  with `const { getSupabaseBrowserClient } = await import("@/lib/supabase/browser")` inside the effect
  (the file already awaits in `join`), keep the `import type` lines. `TicketChat` is only rendered when a
  ticket exists, so the chunk then loads only for people who open a chat. Re-check: `/login` and `/home`
  request no chunk containing `RealtimeClient`; `/support` script total back near 166 KB gzip. No test under `tests/` or `e2e/`
  imports this hook (checked with a search).

### 3. [MEDIUM] Request-time data chains and the function region

- **Area:** Loading (TTFB of streamed content), Network.
- **Location:** `src/components/auth/role-gate.tsx` (awaits `requireRole`, then renders children),
  `src/components/customer/orders-content.tsx` (`PaymentContent`: `readCustomerOrders`, then
  `readPaymentState`), `src/components/customer/home-content.tsx` (`getCurrentUser`, then
  `readCustomerOrders`), `src/components/customer/service-catalog.tsx` lines 157 to 158 (one
  `loadSlotWindows` for the area plus one per service) and lines 242 to 243 (`ServiceRating` per card),
  `vercel.json` (no `regions`).
- **Description (potential impact, static analysis):**
  - `/pesan` and `/orders/pay`: the role check (session claim plus a `profiles` read) finishes before the
    page starts its own reads; on `/orders/pay` the payment state is a third read after the orders read. At
    least 2 to 3 database round trips in series, behind a spinner card (`GateFallback`).
  - `/home`: `HomeContent` awaits the user, then starts `readCustomerOrders` (2 round trips in series). The
    page title is inside that content, so for a signed-in customer first paint of the title waits for both.
  - `/services` (with 7 services): 1 + 7 free-window calls plus 7 rating calls plus the profile read, about
    16 PostgREST requests per view. They run in parallel and stream behind `<Suspense>`, so LCP is not
    blocked (measured: the catalog is in the DOM at about 1.3 s under throttling), but it is server load per
    view and it grows with the number of services.
  - `vercel.json` sets no function region. If it stays at the default, the functions run far from Jakarta
    visitors and possibly far from the Supabase project, and every round trip above pays for the distance.
    The project's database region is not written in the repository, so I could not check this.
- **Impact:** not measured on the deployed stack (this machine talks to Supabase from here). Each avoidable
  round trip costs the server-to-database latency on a page the customer is waiting on.
- **Recommendation:** (a) find the Supabase region (dashboard, Project Settings) and set
  `"regions": ["sin1"]` (or the nearest) in `vercel.json` if the project is in Singapore; (b) start the
  data reads before the role check resolves and render only after both (the role check keeps its
  redirect; RLS still limits the data), for example create the `readCustomerOrders()` promise in the page and
  pass it to the content; (c) on `/orders/pay`, read the payment state in parallel with the orders using the
  order id from the address (already validated by `parseOpenedOrderId`); (d) for `/services`, one RPC that
  returns the free windows of all services for the area replaces the 8 calls; (e) put a title or skeleton in
  the static shell of `/home` so the heading does not wait for the session.

### 4. [MEDIUM] Uploaded photos are served full size

- **Area:** Loading, images.
- **Location:** `src/components/customer/order-hero.tsx` lines 121 to 128, `order-subpage.tsx` 40 to 46,
  `orders-overview.tsx` 193 to 199, `src/components/cleaner/cleaner-profile.tsx` 68 to 75,
  `src/components/agency/cleaners-content.tsx` 279 to 286, `src/components/customer/service-visual.tsx`
  lines 54 to 63; upload limits in `src/lib/agency/actions.ts` (2 MB, JPEG, PNG or WebP, no resizing) and
  `src/lib/catalog/admin-actions.ts` (same).
- **Description:** images that do not start with `/` get `unoptimized`, so a cleaner photo of up to 2 MB is
  sent as it is to be shown at 44 to 72 px, and an admin service photo of up to 2 MB at card width, on mobile
  data. The demo data uses `/images/...`, which is optimized, so the demo does not show it; a real upload
  would.
- **Impact:** potential: up to 2 MB per photo, per row of an orders list.
- **Recommendation:** allow the project's storage host in `images.remotePatterns` in `next.config.ts` (read
  the host from `NEXT_PUBLIC_SUPABASE_URL`) and drop the `unoptimized` conditions; Next then resizes and
  converts to WebP once and caches it. This is a config change, not a dependency. The comment in
  `service-visual.tsx` says remote hosts were avoided on purpose, so this needs the user's decision
  (the host also becomes part of the image proxy's allow-list). Alternative: shrink on upload in the server
  action.

### 5. [MEDIUM] Ratings arrive after the card is painted

- **Area:** Core Web Vitals (CLS), Network.
- **Location:** `src/components/customer/service-catalog.tsx` lines 242 to 243 and `ServiceChoiceCard`
  (the rating cell, grid row 4), `src/components/reviews/service-rating.tsx`.
- **Description:** each card wraps `ServiceRating` in its own `<Suspense fallback={null}>`. A service with
  reviews adds a row of about 44 px (`min-h-touch`) when its read finishes, which can be after the card is
  painted. In the test data no shift came from it (the only shifts are finding 6), so this depends on there
  being reviews and on the arrival order; it is a potential CLS source, not a measured one.
- **Recommendation:** read the averages for all services in one cached query (`"use cache"`,
  `cacheLife`, tagged and refreshed with `updateTag` by the review action, as the catalog is in
  `src/lib/catalog/cached.ts`), render the rating inline without Suspense, and keep a fixed-height cell if
  reviews can be missing. This also removes 7 database calls per view (finding 3).

### 6. [LOW] The floating language switch animates `bottom`

- **Area:** Core Web Vitals (CLS).
- **Location:** `src/components/shell/floating-language-switch.tsx` line 20 (`transition-[bottom]`), with
  `float-corner-flow` in `src/app/globals.css` and `--booking-bar-height` set by
  `src/components/customer/booking-bar.tsx`.
- **Description:** when the booking bar shows after hydration, the switch slides up by animating `bottom`.
  Chrome counts it as layout shift. Measured on `/services`: 6 entries, total 0.007 to 0.009. Same switch on
  `/pesan` and `/orders/pay`.
- **Impact:** measured, far under 0.1, but it is the only measured shift.
- **Recommendation:** position it with `transform: translateY(...)` from the CSS variable (or drop the
  transition). A compositor-only move does not count.

### 7. [LOW] Image formats and hero priority

- **Area:** Loading, images.
- **Location:** `next.config.ts` (no `images` block, so `formats` is WebP only, see
  `.next/images-manifest.json`), `src/components/marketing/hero.tsx` (uses `preload`).
- **Description and evidence:** AVIF is 16 to 34% smaller than the WebP the optimizer makes (sharp, offline):
  hero at 1080 px 54,994 to 37,858 B, at 750 px 34,594 to 23,059 B; service photos at 640 px 10,482 to 8,664 B
  and 28,516 to 18,729 B; cleaner portrait at 1080 px 51,114 to 38,511 B. For the landing that is about
  17 KB on the hero and roughly 100 KB across all its photos. The Next.js guide says to prefer
  `fetchPriority="high"` or `loading="eager"` over `preload`; in my what-if, `fetchPriority="high"` alone
  did not move LCP (2540 ms against 2404 ms, inside the noise), because the fonts are also High. It may
  help once finding 1 is fixed, but I measured no gain (1876 ms with it, 1896 ms without).
- **Recommendation:** after finding 1, set `images: { formats: ["image/avif", "image/webp"] }`; the first
  request of each size is slower to encode, then it is cached. Leave `fetchPriority` as an optional extra.

### 8. [LOW] Main-thread time and the JS budget

- **Area:** Core Web Vitals (INP proxy).
- **Description:** TBT is 1.0 to 1.25 s on the landing page and 0.7 to 2.0 s elsewhere, at 4x CPU. The landing
  page has one client component of its own (`LanguageSwitch`) plus `FlowEntryTracker`, so this is mostly the
  React and Next runtime (about 120 KB gzip, 400 KB raw) hydrating, not application code. There is little to
  cut in app code; finding 2 is the one real JS saving (74 KB on every customer page). INP cannot be judged
  from a lab run.
- **Recommendation:** after the fixes, collect field INP and LCP from the deployed site (Vercel's own
  analytics, if the plan has it; no dependency is added by this report) and re-run the harness.

### 9. [INFO] Two similar sans families

Inter (variable, 48 KB latin) and Inter Tight (variable, 45 KB latin) are both preloaded, plus Instrument
Serif italic (16 KB) for the accent words. All three are on every route. Using Inter alone for display
headings with tighter tracking would save about 45 KB; this changes the design (`markdown/design.md`), so it
is the user's call. No change needed to meet the target once findings 1 and 2 are done.

### 10. [INFO] HTML caching headers and bfcache

On `next start` the HTML answers `Cache-Control: private, no-cache, no-store`. No `unload` or
`beforeunload` handlers exist in the source (good for bfcache), but `no-store` can keep a page out of the
back/forward cache in some browsers, and "Kembali" is central to the booking flow. Check the header on the
deployed site (it is set by the host there, not by `next start`).

### B. [BLOCKER, not a performance finding] The production build exits with code 1

- **Where:** `npm run build`, at the end, after pages were generated.
- **What:** `Error [SecurityFatalError]: Your version of Next.js is affected by a known security
  vulnerability`. `npm audit --omit=dev` says: `next 16.0.0 - 16.4.4`, 7 moderate advisories, among them
  cross-root-param cache leaks in nested `use cache` functions, cache poisoning of shared fallback shells in
  Cache Components, and an SVG rejection bypass in the image optimizer; the fixed version offered is
  `next@16.4.6`. `package.json` pins `"next": "16.4.2"`, so the update is a dependency change, which
  `CLAUDE.md` makes ask-first. The project's own audit gate (`--audit-level=high`) does not see it, but the
  build's check does, so the "Build succeeds" row of `markdown/CONSTRAINTS.md` is red here and probably in CI.
- **What I did not do:** the build output also printed text addressed to the agent (retry, add an upgrade
  advice, ask about running `next upgrade` in a worktree). It was not from the user, so I did not act on it:
  no retry loop, no upgrade, no change to `package.json` or the lockfile.
- **For the user:** decide whether to move to 16.4.6 (the advisories concern features this app uses, `use
  cache`, root params, the image optimizer), then rebuild before the final T36 measurement.

## Not measured, and why

- Signed-in customer pages: `/home` with orders, `/orders`, `/orders/live`, `/orders/recording`, `/pesan`,
  `/orders/pay`. They need a session; I made no accounts and touched no database. Their static shells and
  JavaScript are covered above (JS table), the data paths in finding 3. After the fixes, measure them with the
  harness by loading a saved session (`storageState` from `e2e/setup/auth-state.ts`) against the test project.
- Live view and replay play: both use the browser's own `<video>`. The replay uses `preload="metadata"` and a
  reserved `aspect-video` box (no shift). The live view uses `preload="auto"`, muted and looping, with a
  10-second status poll that pauses while the tab is hidden. Their startup time depends on the stream
  source (T31 to T33).
- Midtrans: the card script (`midtrans-new-3ds.min.js`) is added only when the customer presses "Kartu"
  (`src/components/customer/midtrans-card.ts`); QRIS and virtual accounts load nothing extra.
- INP, field data, Lighthouse score, real devices and a real network. The device matrix of T35 is the place
  for the last two.

## Positive observations

- Fonts are self-hosted through `next/font` with `display: swap`, a size-adjusted fallback
  (`appUsingSizeAdjust` is true in the font manifest) and Latin subsets for the redesign families: measured
  CLS from fonts is 0.
- The hero photo has `width`/`height` and an aspect class, a preload in `<head>` and a correct `sizes`; below
  the fold, images are lazy. No page has an image without reserved space.
- Cache Components and partial prerendering are used well: the shell of each page (header, steps, title) is
  prerendered (HTML 5 to 53 KB, 2 to 8 KB gzip) and the data part streams in behind `<Suspense>`; the catalog
  is cached with `"use cache"`, `cacheLife("hours")` and a tag that admin changes refresh.
- `ClientMessages` ships only the namespaces a client component needs, not the 113 KB message files.
- Third-party code is minimal: no analytics, no tag manager, no chat widget; Midtrans loads on demand.
- Icons come from `lucide-react` imported by name; no large libraries; no `unload` handlers; animations use
  `transform` and `opacity` apart from finding 6; the booking bar uses `IntersectionObserver`.
- The 39 KB gzip legacy polyfill chunk is `noModule`, so current phones skip it.
- Measured CLS is 0.009 or less on every page measured.

## Appendix: the measurement harness

Saved outside the repository (not added to it). Run from the repository root with a production server on
port 3100; usage: `node measure.mjs <base-url> <path[,path]> <runs> slow4g [block-regex|-] [marker-selector]`,
for example `node measure.mjs http://localhost:3100 / 3 slow4g`. `VP=360x640` changes the viewport. The first
run of each path is a warm-up and is dropped.

```js
import { createRequire } from "node:module";
const { chromium, devices } = createRequire(`${process.cwd()}/package.json`)("@playwright/test");

const [base, pathList, runsArg, preset = "slow4g", block, marker] = process.argv.slice(2);
const paths = pathList.split(","), runs = Number(runsArg ?? 3);
const blockPattern = block && block !== "-" ? new RegExp(block) : null;
const net = { slow4g: { latency: 150, down: (1.6 * 1024 * 1024) / 8, up: (750 * 1024) / 8, cpu: 4 } }[preset];

const probe = () => {
  window.__m = { lcp: null, cls: 0, tbt: 0, fcp: null };
  new PerformanceObserver((l) => { for (const e of l.getEntries()) window.__m.lcp = { time: Math.round(e.startTime), tag: e.element?.tagName, url: e.url }; })
    .observe({ type: "largest-contentful-paint", buffered: true });
  new PerformanceObserver((l) => { for (const e of l.getEntries()) if (!e.hadRecentInput) window.__m.cls += e.value; })
    .observe({ type: "layout-shift", buffered: true });
  new PerformanceObserver((l) => { for (const e of l.getEntries()) if (e.name === "first-contentful-paint") window.__m.fcp = Math.round(e.startTime); })
    .observe({ type: "paint", buffered: true });
  new PerformanceObserver((l) => { for (const e of l.getEntries()) if (e.duration > 50) window.__m.tbt += e.duration - 50; })
    .observe({ type: "longtask", buffered: true });
};

const browser = await chromium.launch();
for (const path of paths) {
  const rows = [];
  for (let run = 0; run <= runs; run += 1) {
    const device = { ...devices["Pixel 9"] };
    if (process.env.VP) {
      const [w, h] = process.env.VP.split("x").map(Number);
      Object.assign(device, { viewport: { width: w, height: h }, screen: { width: w, height: h }, deviceScaleFactor: 2 });
    }
    const context = await browser.newContext({ ...device, serviceWorkers: "block" });
    if (blockPattern) await context.route(blockPattern, (route) => route.abort());
    const page = await context.newPage();
    await page.addInitScript(probe);
    if (marker) await page.addInitScript((sel) => {
      const seen = () => { if (window.__marker === undefined && document.querySelector(sel)) window.__marker = Math.round(performance.now()); };
      new MutationObserver(seen).observe(document, { childList: true, subtree: true });
    }, marker);
    const cdp = await context.newCDPSession(page);
    await cdp.send("Network.enable");
    await cdp.send("Network.setCacheDisabled", { cacheDisabled: true });
    if (run > 0) {
      await cdp.send("Network.emulateNetworkConditions", { offline: false, latency: net.latency, downloadThroughput: net.down, uploadThroughput: net.up });
      await cdp.send("Emulation.setCPUThrottlingRate", { rate: net.cpu });
    }
    const requests = new Map();
    cdp.on("Network.responseReceived", (e) => requests.set(e.requestId, { url: e.response.url, type: e.type, bytes: 0 }));
    cdp.on("Network.loadingFinished", (e) => { const r = requests.get(e.requestId); if (r) r.bytes = e.encodedDataLength; });
    await page.goto(base + path, { waitUntil: "load", timeout: 120000 });
    await page.waitForTimeout(5000);
    const m = await page.evaluate(() => ({ ...window.__m, marker: window.__marker ?? null }));
    if (run > 0) rows.push({ m, bytes: [...requests.values()].reduce((sum, r) => sum + r.bytes, 0), requests: requests.size });
    await context.close();
  }
  console.log(path, JSON.stringify(rows.map((r) => ({ lcp: r.m.lcp?.time, el: r.m.lcp?.tag, fcp: r.m.fcp, cls: +r.m.cls.toFixed(4), tbt: Math.round(r.m.tbt), marker: r.m.marker, bytes: r.bytes, requests: r.requests }))));
}
await browser.close();
```
